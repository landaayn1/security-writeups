# SQL Injection в WHERE clause - скрытые данные

**Платформа:** PortSwigger Web Security Academy  
**Тема:** SQL Injection (SQLi)  
**Сложность:** Apprentice (самая лёгкая)  
**Дата:** 15 августа 2026  
**Ссылка:** https://portswigger.net/web-security/sql-injection/lab-retrieve-hidden-data

## Что нужно было сделать

Есть интернет-магазин с фильтром товаров по категориям. 
Например, ссылка выглядит так: https://lab-xxx.web-security-academy.net/filter?category=Gifts

Задача: **найти способ показать ВСЕ товары, включая те, которые скрыты** 
(обычно пользователь их не видит).

Подсказка от платформы: где-то в базе данных есть товары без категории, и они не отображаются. Нужно изменить SQL-запрос так, чтобы они тоже показались.


## Что я поняла про уязвимость

Когда я нажимаю на категорию "Gifts", сайт делает примерно такой запрос к базе данных:

**SELECT * FROM products WHERE category = 'Gifts' AND released = 1**

то есть "Покажи все товары категории Gifts И те, которые опубликованы"

*Есть предположение*, что сайт подставляет то, что я ввожу в URL, непосредственно в базу данных. Тогда получается запрос имеет вид **SELECT * FROM products WHERE category = '[ВВОД]' AND released = 1**
Этот факт можно проверить или опровергнуть, просто подставив кавычку в конец.

# Проверка, есть ли уязвимость
Попробуем в URL добавить /filter?category=Gifts'

**Результат**: Сайт выдал ошибку 500 (Internal Server Error).
**Вывод**: Уязвимость есть! Кавычка сломала SQL-запрос, значит сайт действительно подставляет мой ввод напрямую в базу данных.
**Почему так вышло?** Так как в URL подставлено Gifts', то запрос имеет вид:
**SELECT * FROM products WHERE category = 'Gifts'' AND released = 1**
База данных не понимает, что делать с лишней кавычкой. Это синтаксическая ошибка. Она не может выполнить запрос -> возвращает ошибку серверу -> сервер показывает 500 Internal Server Error.

# Как обойти фильтр и внедрить инъекцию?
Мне нужно, чтобы условие category = '...' стало всегда истинным, тогда покажутся все товары.
Для этого SQL есть трюк: OR 1=1 — это всегда правда (1 всегда равно 1).
Я попробовала такой URL: /filter?category=Gifts' OR 1=1--

**Что значит написанный код?**
Gifts' — закрываю кавычку, которую сайт открыл
OR 1=1 — добавляю условие "ИЛИ правда" -> запрос вернёт все строки
-- — комментарий в SQL, он "закрывает" остаток оригинального запроса (чтобы не было синтаксической ошибки)

## Результат
Открываю этот URL в браузере - и вижу все товары магазина, и надпись "Congratulations, you solved the lab!"
Лабораторная работа пройдена!

## Что я узнала нового?
SQL Injection - это когда сайт подставляет ввод пользователя прямо в запрос к базе данных без проверки.
Кавычка ' - простой способ проверить, есть ли SQLi. Если сайт выдаёт ошибку - уязвимость скорее всего есть.
OR 1=1 - классический трюк, чтобы обойти условие WHERE.
-- - комментарий в SQL, помогает "обрезать" ненужную часть запроса.
Такие уязвимости могут быть очень опасными: через них можно украсть все данные из базы (пароли пользователей, номера карт и т.д.).

## Как это исправить (для разработчика)
Чтобы уберечься от SQL инъекции, нужно сделать так, чтобы ввод пользователя не становился частью SQL запроса.
**Как работает плохой код?**
user_input = "Gifts" 

query = "SELECT * FROM products WHERE category = '" + user_input + "'"
cursor.execute(query)
(cursor.execute запускает на выполнение отдельную SQL-команду или запрос.)

**Что здесь происходит:**
Берётся строка запроса: SELECT * FROM products WHERE category = '
К ней приклеивается ваш ввод: Gifts
В конце приклеивается закрывающая кавычка: '
Получается: SELECT * FROM products WHERE category = 'Gifts'
Этот готовый запрос отправляется в базу

**Как работает хороший код?**
user_input = "Gifts' OR 1=1--"
query = "SELECT * FROM products WHERE category = ?"
cursor.execute(query, (user_input,))

**Что здесь происходит:**
Записываем в user_input пользовательский ввод (даже если пользователь ввёл инъекцию)
В самом запросе (query) мы создаём что-то наподобие заглушки ("?"), которая подразумевает собой, что мы сразу в запрос не вставим значение ввода, а затем передадим его отдельно.
И далее запускаем команду cursor.execute с запросом и вводом, и команда сама уже понимает, что ввод надо вставить вместо заглушки. 
Но БД воспринимает user_input как отдельные данные, а не как часть команды.

База думает: «Мне нужно найти товар, где категория равна тексту Gifts' OR 1=1--». 
Она ищет в таблице строку, где в колонке category написано буквально Gifts' OR 1=1--. Такой строки нет -> возвращает пустой результат.
**Никакого взлома**. Кавычки, OR 1=1, -- — всё это воспринимается как обычный текст, а не как часть SQL-команды.

## Дополнительные меры защиты:
Валидировать ввод (разрешить только буквы/цифры для категории)
Использовать ORM (технология, которая связывает базы данных с объектно-ориентированным кодом) - они сами защищают от SQLi

## Где это встречается в реальной жизни
SQL Injection - это #1 в OWASP Top 10 много лет подряд.
**Реальные примеры:**
Взлом сайтов госучреждений через формы поиска
Утечки баз данных интернет-магазинов
Обход авторизации (' OR 1=1-- в поле логина)
